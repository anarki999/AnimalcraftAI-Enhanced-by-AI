## Update Log（更新日志）

### V1.8（July 28,2026）2026年7月28日

**搜索效率类**

**1. 空步裁剪（Null Move Pruning）**

让引擎在非危急局面下，模拟"让对方连走两步"，若对方仍无法翻盘，说明当前局面优势明显，可提早剪掉这条分支，加速搜索。

**棋力功用**：大幅减少无效分支的计算量，让引擎在同样时间内能把节省下来的算力投入更深层的搜索，等效提升实战中的思考深度。


**2. 前置裁剪（Futility Pruning）**

在剩余深度仅1~3层、非危急局面时，若静态评估加上该深度的最大可能改善幅度仍追不上alpha，直接放弃深入搜索该节点，节省大量无意义运算。

**棋力功用**：专门加速搜索树末端（叶节点附近）的处理效率，让引擎能把省下的时间分配到更关键的中局分支，间接提升整体搜索深度与速度。


**3. 浮动比例削减后期走法裁剪（Late Move Reduction）**

原本固定砍1层深度，改为用 log(深度)×log(着法序号) 算出浮动削减量；历史表分数高的走法（过去表现佳）削减力度会减轻，让排序靠后的"冷门"走法搜得浅、热门走法搜得深。

**棋力功用**：比固定砍1层更精准地分配算力——不会因排序机制的偶然误差而错杀潜在好棋，同时对明显的差棋加大削减幅度，让引擎在有限时间内把资源集中在真正有价值的分支上，兼顾速度与正确性。


**4. 价值裁剪（Delta Pruning，用于静态搜索）**

在Quiescence吃子搜索中，若某个吃子走法即使成功也不可能把分数拉回alpha以上，直接跳过该分支，减少无意义的深搜。

**棋力功用**：让静态搜索（处理吃子连锁反应的关键环节）更快收敛，避免在明显无望的吃子线上浪费算力，确保引擎能在时间限制内把战术计算做得更完整。


**5. 渐进式重搜望孔窗口（Aspiration Window）**

迭代加深時仍以窄視窗（上一層分數 ±50）起跳，但一旦偵測到近似殺棋分數（abs(vlBest) >= WIN_VALUE），不再使用每次 ±200 分微調的方案，而是直接把 aspiration window 打開到全域

**棋力功用**：本身不改变引擎的判断准确度，而是用更省时的方式达到同样正确的结果——省下的时间可转化为多算1层甚至半层的深度，在固定时限的对局中，搜索深度每增加1层通常能带来明显的棋力提升；同时避免大幅重搜造成的耗时波动，让迭代加深节奏更稳定，也更利于Lazy SMP多线程下把节省的算力有效转化为整体吞吐量提升。


**6. 将军延伸（Check Extension）**

若某一步直接威胁入穴（叫杀），搜索深度不减1层，让引擎多算一层确认这步棋的真实性，避免误判。

**棋力功用**：防止引擎在搜索深度受限时，把"看似能叫杀但实际上是虚招"的走法误判为好棋，提升关键战术局面下的判断可靠度，减少因搜索深度不足导致的漏算。


**7. 后台思考模式（Background Thinking / Infinite Mode）**

新增 go infinite 指令支持，透过 bInfinite 旗标让引擎在没有时间上限的情况下持续迭代加深搜索，直到收到GUI发出的 stop 指令才停止；期间引擎会持续透过 info depth、info time nodes 等讯息即时回报当前搜索进度与节点数，供GUI端同步显示。

**棋力功用**：让引擎能在对手思考、或轮到玩家走棋的空档持续分析局面（也就是象棋引擎常说的"后台思考"/Ponder），不浪费任何可用的运算时间；配合UCCI协议的 stop 指令，GUI可以随时打断分析并立即取得当下最佳结果，兼顾深度搜索与响应速度，让引擎在实际对局中能更充分利用每一秒可用时间，变相提升有效搜索深度与棋力表现。

**8. 单一延伸与反向多切裁剪（Singular Extension & Reverse Multi-Cut）**

针对零窗口测试(PVS)结果"差一点点被剪掉"的走法（分数落在alpha下方SINGULAR_MARGIN=30分的窄区间内），且该走法排序在前REVERSE_MULTICUT_RANK_LIMIT=3名以内时，用多算SINGULAR_EXT_DEPTH=2层的深度重新做一次零窗口验证，通过才升级为完整窗口确认精确分数；其余排序靠后的走法维持原本裁剪效率不受影响，只对"有嫌疑"的候选花额外算力。

**棋力功用**：专门解决零窗口测试对"弃子换攻杀"、"多子vs多兵"这类延迟收益招法容易误判fail-low的问题，避免真正的好棋因浅层评估分数暂时偏低而被过早剪掉；由于只对排序靠前、少数可疑的走法做二次确认，额外开销可控，能在不明显拖慢整体搜索速度的前提下，提升引擎对战术性、延迟收益招法的判断准确度。

**9. 浮动比例削减后期走法裁剪条件细化（LMR Finetuning）**

原本的 LMR（Late Move Reduction）主要依赖「走法序号」、「搜寻深度」与「静态历史表分数」来决定减深幅度。新版额外纳入了 杀手走法 (Killer Move)、反击走法 (Counter Move) 与 接续历史表 (Continuation History) 作为保护条件。如果某个安静走法命中这些「曾经证明有效」的上下文特徵，引擎将减少甚至取消对它的减深惩罚。

**棋力功用**： 让 LMR 真正做到「把晚出现且不重要的走法减深」，而不是单纯盲目砍掉所有晚搜的棋。避免引擎把具有强烈战术反击潜力、或是曾成功过的好棋（Killer/Counter）误判为无用而减得太浅，从而在不增加总节点数的前提下，显着减少 Fail-High 后需要重搜的频率，提升整体搜寻稳定性。

**10. 将军局面免除后期走法削减（LMR In-Check Guard）**

在决定是否对静态走法进行 LMR 减深时，新增了「若该走法会造成将军 (Gives Check) 则不削减」的保护条件（!bGivesCheck），同时也确保了「己方正被将军时的应对走法 (In-Check)」绝对不被减深。这些条件都是直接複用已算好的深度资讯，零额外运算成本。

**棋力功用**： 会造成将军的走法通常带有强烈的战术意图与后续连锁反应，若被 LMR 误减，很容易漏算关键杀着或弃子战术。这项修补将「将军延伸 (Check Extension)」与 LMR 逻辑完全对齐，确保引擎在攻杀激烈的局面下不会因为排名的偶然性而错过致命一击。

**11. 静态交换评估排序与静态搜寻负交换剪枝（SEE-based Quiescence Pruning）**

在 Quiescence Search（静态搜寻）中引入静态交换评估（Static Exchange Evaluation, SEE）。引擎在生成吃子走法时，会预先计算该格子连续换子的淨值（SEE Score）。这个分数不仅用来让吃子走法排序更精准，更作为明确的剪枝门槛：凡是 SEE <= -MATE_VALUE 的非法吃子直接略过；对于明显亏损的吃子（SEE < 0 且即使加上 SEE 淨值也追不上 alpha），直接做负交换剪枝 (Negative SEE Pruning)。

**棋力功用**： 这是对原本 Delta Pruning 的强力升级。原本只看单颗被吃子的价值，现在能精准预判「吃过去之后会不会被对方反吃回来而大亏」。在近杀或子力纠缠的局面中，这能替 Quiescence Search 剪掉大量看似能吃子、实则送死的「纯噪音」分支，让静态搜寻收敛得更快、更乾淨，大幅节省算力。


**评估精准度类**

**12. 威胁度评估（Threat Evaluation）**

新增 EvalThreat() 函式，逐一检查己方每颗棋子是否正被对方棋子合法威胁（含跳河攻击），依棋子等级给予不同扣分幅度（象扣最重、猫扣最轻），让静态评估更贴近真实战术局面。

**棋力功用**：让引擎在尚未深入搜索前，就能对"棋子正被威胁"的局面提前警觉并降低评分，减少因单纯比较子力价值而忽略战术风险所导致的误判，尤其能提升引擎在防守与应对威胁时的判断品质。


**13. 简化版修正历史机制（Correction History Lite）**

用一个仅8格的小数组，按棋子种类记录"本层与上层分数落差"的指数滑动平均(EMA)修正值，微调Evaluate()的静态评估，帮助引擎更快收敛到准确评价，且几乎零额外开销。

**棋力功用**：让静态评估随着搜索层数推进逐步自我校正，减少评估函式的系统性偏差，使引擎对局面优劣的判断更快趋于准确，尤其有助于改善浅层搜索时的评分稳定性，且几乎不增加额外运算负担。

**14. 修正历史表同节点重複加分消除（No Double Best-Move Reward）**

修正了原本在根节点与主搜寻函式（SearchFull / SearchRootWindow）中，同一个 Best Move 发生 Fail-High 切断时会被加分一次、然后在节点尾端又被 SetBestMove 重複加分一次的问题。新版移除了尾端多余的奖励，让 History Heuristic 的学习信号回归单纯的「切断与竞争者对比」。

**棋力功用**： 避免某些最佳走法（PV / Best Move）在同层被不成比例地「Double Reward」而导致分数无限膨胀。这让历史表（History Table）和吃子历史表（Capture History）的统计分布更加健康、客观，直接提升了 Move Ordering（走法排序）的准确率。

**15. 简化版修正历史机制精准化（Correction History Tuning）**

修正了原先 UpdateCorrHist() 在纪录「移动的棋子」时，误拿目标格（DST）来作为分类桶位（Bucket）的 Bug，改为正确读取起始格（SRC）。同时，进一步将更新条件收紧：只有当最佳走法是「非吃子（Quiet Move）」，且本层与上层分数确实有落差时才写入纪录。

**棋力功用**： 修正了评估修正表（Correction History）记错桶位的根本性失真问题；并透过排除吃子走法（Capture），避免了激烈的战术波动把高噪音的短期分数差写进长期修正表里。这让引擎的静态评估（Static Eval）校正更加稳定可靠，有效提升了引擎判断局面长期优劣的「大局观」。


**多线程架构类**

**16. 惰性对称多处理多线程搜索（Lazy SMP）**

将 mvResult、历史表、杀手走法表等改为 thread_local 独立变数，各线程各自完整执行 MultiPV 迭代加深迴圈，并共用同一份置换表（g_HashTable）。透过 atomic 变数同步停止讯号与节点计数，主线程负责输出 info／bestmove，其余 worker 线程专注于贡献置换表内容与各自的搜寻结果。

**棋力功用**：在保留 Lazy SMP「共享 TT、独立搜索」理念的前提下，让所有线程都能对同一局面做完整深度探索，再由「最佳线程选择（best thread voting）」机制决定最终 bestmove，比单纯只採用主线程结果更能发挥多核 CPU 的搜寻多样性与深度优势。


**记忆体优化类**

**17. 置换表容量调整（Hash Table Size Adjustment）**

HASH_SIZE 由固定 1<<20（约 100 万项）改为依 HashMB=<N> 配置的动态分配，单位为 MB，并向下取最接近的 2 的幂作为 bucket 数量，方便用 bitmask 取余。预设大小为 1024MB，可透过 engine.ini 或 UCI 风格指令 setoption name Hash value <N> 在 runtime 调整，并自动重新分配与清空置换表。

**棋力功用**：让引擎可以依不同机器环境动态调整置换表记忆体使用量，在低记忆体环境避免吃掉过多 RAM，在高记忆体环境则能配置更大的 TT 降低碰撞率，兼顾稳定性与性能。

**18. 置换表项结构体栏位精简与双层替换策略（HashItem Struct Compaction & Two-Slot Replacement）**

评估分数栏位由 int 改为 short，缩小每个置换表项的记忆体佔用；同时将原本单一 slot 的 HashEntry 改为每个 bucket 两个 slot：一个 depthPreferred 专门保留同局面中「搜索深度较高」的结果（只有新结果深度 ≥ 旧结果或 lock 相同时才复盖），另一个 alwaysReplace 则永远写入最新结果，确保浅层但高频重複出现的局面永远有一个最新命中。

**棋力功用**：在同样记忆体预算下容纳更多、有区分策略的置换表资料，一方面降低碰撞、保留深层关键结果，一方面让开局等重複局面也能维持最新资讯，不会被深度优先 slot 长期佔位，整体提升 TT 的「记忆品质」与实战稳定性。


**架構與穩定性修复类**

**19. 非同步搜索线程棋局同步修復（Async Search Thread Position Sync Fix）**

之前将 SearchMain 改为丢到独立线程 g_searchThread 执行，让主程式能持续读取 stop/ponderhit 指令，但棋局资料 pos 在每条线程里都是各自独立的一份，新线程启动时并未从主线程把当前真实棋局复制过去，导致该线程拿到的其实是一个从未摆过任何棋子的空棋盘，在这个空棋盘上搜索自然找不到任何有效走法。修复方式为在派发新线程之前，先让主线程把当下棋局的完整快照传给 SearchMain，确保搜索线程一启动就基于正确的棋局进行计算。

**棋力功用**：属于关键正确性修复，解决了引擎在异步化搜索架构下"算出无效着法、bestmove 输出乱码"的严重缺陷，确保每次 go 指令启动的搜索都基于真实棋局进行，是多线程UCCI通信改造能够正常运作的前提。

**20. Stop指令即时响应修复（Immediate Stop Response Fix）**

SearchFull 原本在判断是否要提前中断搜索时，误加了一个"只有非主搜索线程才生效"的额外条件，导致负责执行主要搜索流程的那条线程完全不会检查停止信号，收到 stop 指令后仍会把当前这一整层的搜索跑完（深度较高时可能耗时数秒至数十秒）才真正停下。修复方式为移除这个多余的条件，让所有线程一律平等地检查停止信号，并在根节点走法枚举的迴圈（SearchRootWindow）里额外加入检查点，让停止指令能在每算完一个候选走法后就立刻生效。

实作上除了让所有线程一律检查全域停止旗标外，还引入 PollTimeAndMaybeStop() 以固定节点数间隔（2048 节点）在 SearchFull / SearchQuiesc 内部主动轮询，并在根节点走法迴圈中同步检查，使 stop 指令不再只在整层完成时才生效，而是能在深度搜索过程中快速响应。

**棋力功用**：让引擎在实战与GUI操作时能真正做到"随时可打断"，避免因深度暴增、节点数暴涨（如深度12单层即耗费近1000万节点）而卡住数秒才响应停止指令，大幅改善引擎的实用性与操作体验，避免因响应延迟被判超时或误判引擎当机。

**21. Ponderhit指令即时响应修复（Immediate Ponderhit Response Fix）**

ponderhit 指令原本只重设计时起点并解除"后台思考不计时"的豁免状态，但引擎检查时间是否用完的动作，原本只安排在每一层搜索完整跑完之后才执行一次。如果 ponderhit 送达时刚好碰上正在进行一层特别深、特别耗时的搜索（后台思考期间因不受时间限制可以无限深搜），就会导致时间早已用完，却要等这一层彻底跑完才真正停下来。修复方式为新增一个独立的超时检查，并同样加进 SearchRootWindow 的根节点走法迴圈里，让主线程在每算完一个候选走法时都主动确认时间是否已经用完，一旦超时就立刻发出全域停止信号，让搜索马上结束。

**棋力功用**：让"后台思考(Pondering)→对手真实落子→ponderhit"这一实战最常见的流程，能确保引擎在剩余时间预算耗尽时准确、及时地给出 bestmove，而不会因pondering期间累积的超深搜索状态而拖长响应时间，是让第7项"后台思考模式"真正能安全落地于实战对局的必要配套修复。
